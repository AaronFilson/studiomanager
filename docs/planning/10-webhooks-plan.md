# Wave 2, item 3: outbound webhooks

_Planned 2026-11-02. Item 3 in [08](08-wave2-queue.md), on `wave2-webhooks`._

## Why

The integration owners ask for is "you cannot connect Zapier" ([03](03-tools-in-use.md)). A
signed HTTPS POST per event covers Zapier's "Webhooks by Zapier" catch hook, Make, n8n, Pipedream
and a studio's own script. None of them needs an app listing or a partner account, so this can be
built and tested without anyone's credentials.

## The first events

| Type | Raised from | Payload `data` |
|---|---|---|
| `pieces.ready` | `FiringCompleted` | the firing (kind, kiln, ended at), then one entry per maker: member id, name, email, and their pieces (number, description, collect by). One event per firing, grouped the way the notices are, so a Zap doesn't fire 30 times. |
| `fee.charged` | `PieceReceived` (firing fee) and `SupplySold` | member id, name, email, what it was for, amount, currency, tax category, when. |
| `member.joined` | `MemberJoined` | member id, name, email, role, joined at. |
| `ping` | the "Send test" button | studio id and name only. |

Questions to settle while building:
- Is "fee charged" every charge to a member's balance, including membership and class fees once
  they exist? Name it after the ledger posting, not the cause, so new causes join without a new
  type. Start with the two sources above.
- Payloads carry the member's name and email, which is what makes a Zap useful. Only staff can
  add an endpoint, and the form says that member details leave the studio.

**The envelope** (versioned from the start):

```json
{ "id": "evt_…", "type": "pieces.ready", "version": 1, "created_at": "2026-11-02T18:04:00Z",
  "studio": { "id": "…", "name": "…" }, "data": { … } }
```

Money is a decimal string with a currency, the same as the API. Times are UTC ISO-8601.

## Design

### Endpoints
- New table `webhook_endpoint`, under tenant RLS:
  - `url`, `description`, `event_types text[]`, `enabled`
  - `secret`
  - `created_by`, `created_at`
  - `disabled_reason`, `consecutive_failures`
- Staff and owners manage endpoints. A studio can have up to 10.
- **The secret** is generated by the server (`whsec_` + 32 random bytes) and shown once, at
  creation or rotation. It has to be stored readable to sign with, so it's encrypted at rest with
  AES-GCM under a key from config. At deploy that key comes from Key Vault through managed
  identity, the same as the planned provider OAuth tokens.
- Rotating keeps the old secret valid for 24 hours, and both signatures are sent in that window.

### Signing: the Standard Webhooks scheme
Follow <https://www.standardwebhooks.com/> rather than inventing headers. It's what Svix, Clerk
and others use, and receivers have libraries for it.
- `webhook-id` is the event id, so receivers can drop duplicates.
- `webhook-timestamp` is in Unix seconds.
- `webhook-signature` is `v1,<base64 HMAC-SHA256 of "id.timestamp.body">`. The value is
  space-separated during a rotation.

### From event to delivery: at least once, with nothing lost on rollback
1. **In the business transaction.** A `WebhookFanOut` `@EventListener` runs synchronously, like
   `NotificationService`. It finds the enabled endpoints subscribed to the type and inserts:
   - one `webhook_event` row, holding the payload;
   - one `webhook_delivery` row per endpoint, `PENDING`, with `next_attempt_at = now`.

   If the work rolls back, so do these.
2. **It then publishes `WebhookDeliveryRequested(deliveryId, studioId)` to the outbox.** It
   carries only ids, as `InviteEmailRequested` does, so member emails don't sit in
   `event_publication` for 30 days. After commit, an async listener binds the studio and makes
   the first attempt straight away.
3. **The delivery row handles retries, not the outbox.** Webhooks need a longer, growing
   backoff than email's flat 5 minutes × 8:
   - 1 m, 5 m, 30 m, 2 h, 6 h, 12 h, then every 24 h, about 3 days in all;
   - each attempt records its status code, latency and the first 1 KB of the response.

   A scheduled sweeper (every minute) claims the due rows across studios. It does that through a
   security-definer function, as in [ADR 10](../adr/0010-security-definer-functions-for-cross-tenant-work.md),
   with `for update skip locked`, so two instances never send the same attempt at once.
4. **Success** is any 2xx within 10 seconds. A 410 Gone disables the endpoint at once.
5. **When an endpoint keeps failing.** After 3 days of failures, or 50 failures in a row, it is
   disabled. Staff get a `WEBHOOK_DISABLED` notice through the normal notification path, so it is
   emailed too. Re-enabling it does not replay what it missed; staff can resend from the log.
6. **Scale to zero.** Retries run only while an instance is up, the same as email (ADR 11). The
   first attempt happens on the request that caused it, so the usual case is unaffected.

Delivery is at least once, and the docs say so. Receivers dedupe on `webhook-id`. Order isn't
guaranteed, and receivers are told to use `created_at`.

### The SSRF filter (`platform.http.SafeHttpClient`)
The studio types the URL, so the server will POST wherever it points. The filter is shared, so
the later integrations reuse it:
- **Scheme and port.** `https` only, on port 443 or 8443. The `local` profile also allows
  `http://localhost`, for tests and demos.
- **Checked when saved and again before every send.** Resolve every A and AAAA record. Reject the
  URL if any address is one of these:
  - loopback, private (RFC 1918), link-local (including `169.254.169.254`, the metadata
    endpoint), CGNAT `100.64/10`, multicast, broadcast or unspecified;
  - IPv6 ULA `fc00::/7`, or an IPv4-mapped or NAT64 form of any of the above.
- **Connect to the address that was checked.** That stops DNS rebinding. Keep the hostname for
  SNI and certificate checks. The JDK `HttpClient` can't pin an address, so this needs a resolver
  hook. Use Apache HttpClient 5's `DnsResolver`, or a JDK socket factory, and pick whichever is
  simpler under test.
- **Limits on each request.**
  - Redirects are not followed; a 3xx is a failure.
  - 5 s to connect and 10 s in total.
  - At most 64 KB of the response is read.
  - The request has no cookies and no proxy, and its User-Agent is `StudioManager-Webhooks/1`.
- **Rejections are explained.** A rejected URL says why: "resolves to a private address" is
  shown to staff, not hidden.

### API (contract first, in `studiomanager.yaml`)
- `GET/POST /webhooks/endpoints`, and `GET/PATCH/DELETE /webhooks/endpoints/{id}`. The secret is
  returned only by POST and by rotation.
- `POST /webhooks/endpoints/{id}/rotate-secret` and `POST /webhooks/endpoints/{id}/test`, which
  sends `ping` straight away and returns the result.
- `GET /webhooks/endpoints/{id}/deliveries`: the last 30 days, newest first, each with its
  attempts.
- `POST /webhooks/deliveries/{id}/resend`.
- `GET /webhooks/event-types`: the list, with an example payload for each. The web page shows
  these, so a Zapier user can map fields before the first real event.

### Web
There's a "Webhooks" page under Settings, for staff only. It has:
- a list of endpoints, and an add form: URL, which events, and a description;
- the secret, shown once with a copy button;
- a "Send test" button;
- a delivery log for each endpoint, with its status, response code and a resend button;
- a short "Connect Zapier" how-to: Catch Hook, then paste the URL, then Send test.

### Data
- V23 adds `webhook_endpoint`, `webhook_event`, `webhook_delivery` and `webhook_attempt`, with
  RLS on all four.
- Events and deliveries are purged after 30 days, alongside `OutboxRetry.purgeCompleted`.
- The studio export ([04](04-pilot-readiness-plan.md)) includes the endpoints, without secrets.

## Tests
- **Unit.**
  - Signing is checked against the Standard Webhooks spec's published test vectors.
  - The backoff schedule.
  - The SSRF classifier, over an address table: every blocked range, the mapped and NAT64 forms,
    and decimal or octal IP spellings in the URL.
- **Integration** (Testcontainers, and a local HTTPS receiver such as WireMock):
  - a rollback leaves no delivery;
  - each event type produces the documented payload;
  - a 500 is retried, then succeeds;
  - 410 disables the endpoint;
  - a disabled endpoint raises the staff notice;
  - two sweepers never double-send;
  - RLS keeps one studio's endpoints and log from another;
  - a hostname that resolves to `127.0.0.1` is refused, even under the `local` profile when the
    URL says `https`.
- **Web.** A Playwright test that adds an endpoint, sends a test, and sees it in the log.

## Not in this slice
- Inbound webhooks: the kiln-controller receiver, and creating members from storefront orders.
- A listed Zapier or Make app with triggers and auth. The catch hook covers it for now.
- API keys for pulling data, filtering on payload fields, and custom headers on endpoints.
- More event types: payout recorded, consignment sold, maintenance due. They're cheap to add
  once the fan-out exists.

## Later: streaming events to Kafka (resume work, after this slice)

The fan-out already turns domain events (`FiringCompleted`, `PieceReceived`, `SupplySold`,
`MemberJoined`) into one outbound stream. Spring Modulith can also publish those events to a
broker with `@Externalized` (`spring-modulith-events-kafka`), through the same outbox (ADR 11), so
the business code doesn't change.
- **Locally:** Kafka (or Redpanda) in WSL Docker, and Testcontainers in CI.
- **A consumer worth showing:** an analytics projection (firings per kiln, fees per week), or
  webhook fan-out moved onto the stream.
- **Deployed:** optional. Azure Event Hubs' Kafka endpoint needs the Standard tier (paid), and
  the API scales to zero, so it stays behind a flag until there's a reason to pay for it.

## Status

First version done 2026-11-02 (V23), on `wave2-webhooks`. It follows the design above, with these
changes:
- **No outbox event for the first attempt.** Deliveries are written in the business transaction.
  The first attempt runs right after commit, and the sweep is the safety net: it waits 1 minute
  before taking over a new delivery. Only `member.joined` goes through the outbox (an async
  after-commit listener), because it's raised outside any studio.
- **Test.** "Send test" stores a `ping` event and attempts it synchronously, so the log shows it.
- **Open at deploy.** `STUDIOMANAGER_WEBHOOK_SECRET_KEY` has to come from Key Vault (wire it into
  `infra/modules/api`). The azure profile has no default, so the API won't start without it.
- **Not yet.** The Playwright test (there are vitest page tests and API integration tests).

## Decisions to record
**ADR 14: outbound webhooks.** The Standard Webhooks signing, delivery rows that own their
retries beside the outbox, the SSRF filter with a pinned address, and at least once with dedupe
by id.

**In an interview:** "The studio types a URL and my server POSTs to it, so it's an SSRF hole
unless I resolve it, check every address, and connect to the address I checked. Deliveries are
written in the business transaction, so a rollback sends nothing. They're signed the Standard
Webhooks way, and they retry with backoff until the endpoint is disabled and staff are told."
